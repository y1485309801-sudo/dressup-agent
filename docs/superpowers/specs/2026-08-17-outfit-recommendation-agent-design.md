# 穿搭推荐 Agent 设计规格

日期：2026-08-17  
状态：已完成对话设计确认，等待书面规格复核

## 1. 产品目标

在现有 Dressup 虚拟衣橱原型中增加一个穿搭推荐 Agent。用户首次设置常住城市并录入衣物后，可以用自然语言描述当天活动，系统结合实时天气、个人偏好和衣橱现有衣物，返回 2～3 套可视化穿搭方案，并支持连续对话调整。

第一阶段只推荐用户已经拥有且状态为“可穿”的衣服。系统不得加入虚构单品、外部商品或购买链接；如果衣橱无法满足条件，应明确说明缺少的衣物类别。

## 2. 成功标准

- 用户只需设置一次常住城市，之后推荐时自动查询对应地点和日期的天气。
- 上传衣物后，系统自动生成可编辑的结构化标签。
- 用户输入一句自然语言需求后，得到 2～3 套由真实衣橱单品组成的方案。
- 推荐结果覆盖天气适配、场合适配、颜色协调、风格偏好和近期穿着频率。
- “正式一点”“不要这条裤子”“保留外套换一套”等追问能基于当前会话局部调整。
- 结果可收藏、记录为今日穿搭、加入日历或进入现有 AI 试穿流程。
- 天气、标签识别或 Agent 服务失败时有明确降级路径。
- 服务端返回结果在展示前经过衣物 ID 校验，绝不展示不存在或不可穿的衣物。

## 3. 第一阶段范围

### 3.1 底部导航

底部导航调整为五个入口：

1. 推荐：默认首页，承载天气、Agent 对话和穿搭卡片。
2. 衣橱：录入、查看、编辑和管理衣物。
3. 换装：保留现有即梦 AI 试穿能力。
4. 日历：查看真实穿搭和未来计划。
5. 我的：管理城市、偏好、温感、禁忌和学习记录。

### 3.2 首次设置与个人画像

首次进入推荐页时显示轻量设置流程，收集：

- 常住城市。
- 温感：怕冷、正常、怕热。
- 常穿风格，可多选。
- 喜欢和避开的颜色。
- 明确禁忌，例如不穿裙子、不穿高跟鞋。
- 是否接受配饰推荐。

不要求填写身高、体重、体型、肤色或尺码。以上信息均可在“我的”中修改或重置。

### 3.3 天气能力

天气服务应提供：

- 当前温度和体感温度。
- 当日最高、最低温度。
- 天气现象和降雨概率。
- 风力和湿度。
- 数据更新时间。

请求中出现“明天”“周五”或其他城市时，优先使用请求中的日期和地点；否则使用当前日期和常住城市。天气结果在短时间内缓存，避免重复调用。

天气接口失败时优先使用仍在有效期内的缓存；缓存也不可用时，引导用户手动填写温度和天气，不得把过期数据当作实时数据。

### 3.4 衣物自动标签

现有衣橱字段在图片、分类、颜色、收藏和穿着次数基础上扩展为：

- 一级分类和二级类型。
- 主色、辅助色和图案。
- 材质推测。
- 厚度：薄、中等、厚。
- 适用季节。
- 保暖等级。
- 正式度。
- 风格标签。
- 防风、防水等功能属性。
- 标签来源和识别置信度。
- 状态：可穿、清洗中、暂时收纳、停用。

上传图片后由支持图片理解的模型返回结构化 JSON。用户在保存前可以修改全部标签；低置信度字段需要突出提示确认。识别失败时保留现有手动分类与颜色流程，并允许稍后重新识别。

### 3.5 推荐首页与对话

推荐首页包含：

- 城市和今日天气摘要。
- 对话消息列表。
- 快捷场景：上班、约会、见客户、聚会、旅行、休闲。
- 自然语言输入框。
- 最近推荐入口。

Agent 从用户输入中提取日期、地点、活动、室内外、正式度、步行量、持续时间、着装要求和临时偏好。信息足够时直接推荐；只有关键条件缺失且会显著改变结果时才追问一个问题。

### 3.6 推荐结果

默认返回三种定位不同的方案：

- 方案 A：最稳妥。
- 方案 B：更舒适。
- 方案 C：更有风格。

衣橱组合不足时允许返回一套或两套，但不允许用不存在的衣物凑足数量。每套方案展示：

- 用户真实衣物图片组成的搭配卡片。
- 上衣、下装、外套、鞋和可选配饰。
- 推荐理由。
- 适合温度和场景。
- “穿这套”“换一套”“收藏”“加入日历”“AI 试穿”“不喜欢”操作。

“AI 试穿”复用现有即梦流程，只有用户主动点击时才生成，不作为每次推荐的前置步骤。

### 3.7 连续对话

当前推荐会话保存解析后的约束、候选方案和用户的局部修改。支持：

- 整套重选。
- 更正式或更休闲。
- 更保暖或更凉爽。
- 排除指定单品、类别或颜色。
- 锁定某件衣服，只替换其他部分。
- 避免重复昨天或最近穿过的组合。

每次调整后仍需执行衣物 ID 和可用状态校验。

### 3.8 反馈与学习

支持显式反馈：喜欢、不喜欢、今天穿了、太冷、太热、太正式、太休闲、不喜欢颜色、不喜欢某件衣服。

反馈用于更新本地偏好权重和近期排除项。用户可以在“我的”中查看和重置学习结果。第一阶段不建立不可解释的长期画像；每项自动学习都保留来源和可撤销能力。

### 3.9 日历联动

- “穿这套”将方案记录为今日真实穿搭，增加各衣物穿着次数并更新最后穿着时间。
- “加入日历”保存为计划穿搭。
- 到计划日期时重新用最新天气检查；若明显不合适，提示用户重新推荐，但不自动覆盖原计划。

## 4. 推荐技术方案

采用“硬约束过滤 + 组合评分 + 大模型解释”的混合方案，不采用纯大模型直接选衣。

### 4.1 数据流

1. 意图解析器把用户文本转换为结构化场景约束。
2. 天气服务根据日期和地点获取天气快照。
3. 衣橱查询只返回状态为“可穿”的真实衣物。
4. 规则层排除季节、温度、降雨、场合和用户禁忌不合适的单品。
5. 组合器按类别生成有限数量的完整穿搭候选。
6. 评分器按天气、场合、个人偏好、颜色协调和近期重复度排序并保证结果多样性。
7. 对话模型只在候选范围内选择、解释和响应追问。
8. 校验器核对所有衣物 ID、状态和方案完整性后才返回前端。

### 4.2 推荐权重

初始权重如下，后续可根据反馈微调：

- 天气适配：30%。
- 场合与正式度：25%。
- 用户风格和禁忌：20%。
- 颜色与组合协调：15%。
- 近期穿着、重复度和可用状态：10%。

天气、禁忌和衣物可用状态属于硬约束，不能仅靠总分抵消。

### 4.3 Agent 工具边界

Agent 通过明确工具调用访问数据，不直接读取或修改任意前端状态：

- `get_profile`：读取城市和偏好。
- `get_weather`：读取指定城市与日期的天气。
- `search_wardrobe`：按结构化条件查询衣物。
- `recommend_outfits`：运行过滤、组合和评分。
- `save_feedback`：保存用户反馈。
- `save_outfit`：收藏、记录今日穿搭或加入日历。

工具输出均为结构化数据。模型返回的任何衣物 ID 必须存在于工具给出的候选集合中。

## 5. 本地数据模型

第一阶段维持单用户、本地优先模式，不实现登录和云同步。新增数据实体：

- `profile`：城市、温感、风格、颜色偏好和禁忌。
- `garments`：衣物图片、扩展标签、状态、穿着次数和时间。
- `weather_cache`：城市、日期、天气快照、获取时间和过期时间。
- `recommendation_sessions`：原始请求、结构化约束、方案和会话上下文。
- `feedback_events`：反馈类型、目标方案或衣物、时间。
- `outfit_history`：真实穿搭、计划穿搭和收藏。

继续使用浏览器本地存储，但通过独立数据访问模块封装，不允许新页面直接散落调用 `localStorage`。图片继续使用压缩后的本地数据；接近浏览器存储上限时给出明确提示。

## 6. 服务端接口

在现有 Node.js 服务上增加：

- `POST /api/garments/analyze`：分析衣物图片并返回结构化标签。
- `POST /api/weather`：查询并缓存天气。
- `POST /api/agent/recommend`：解析需求并生成穿搭方案。
- `POST /api/agent/refine`：根据会话和新约束调整方案。

图片理解和对话模型通过服务端提供者适配层调用。提供者配置只存在于环境变量中；前端不保存任何密钥。若未配置模型，衣物仍可手动录入，但 Agent 页面明确显示服务未配置，不伪造 AI 结果。

## 7. 安全与隐私

- 立即移除并轮换现有测试脚本中疑似泄露的火山引擎 AK/SK。
- 所有密钥迁移到服务端环境变量。
- 限制跨域来源、请求体大小和请求频率。
- 上传图片使用有时效的随机地址并自动清理。
- 日志不得记录密钥、完整人物照片、完整 base64 或敏感画像。
- 标签分析只上传完成任务所需的图片，不把人物照片用于衣物识别。

## 8. 异常与降级

- 天气失败：使用有效缓存；否则请求手动天气。
- 标签识别失败：进入手动编辑，不阻断衣物保存。
- 对话模型失败：保留用户输入和当前会话，允许重试。
- 推荐组合不足：返回实际可用数量并解释衣橱缺口。
- 非法衣物 ID：服务端丢弃方案并重新生成一次；仍失败则返回明确错误。
- 网络中断：不清空当前对话和已选衣物。
- 本地存储接近上限：阻止继续写入大图并提示清理或导出数据。

## 9. 测试策略

### 9.1 单元测试

- 日期、地点和场景解析。
- 天气缓存和过期处理。
- 硬约束过滤。
- 颜色、正式度和重复度评分。
- 组合多样性。
- 衣物 ID 与状态校验。
- 用户反馈权重更新。

### 9.2 接口测试

- 图片识别成功、低置信度、超时和失败。
- 天气成功、缓存、失败和手动降级。
- 首次推荐和连续调整。
- 模型返回虚构衣物 ID 时的拒绝逻辑。

### 9.3 端到端测试

- 首次设置城市和画像。
- 上传衣物、AI 标签、人工修改并保存。
- 输入场景并获得真实衣橱方案。
- “不要这条裤子”后正确替换。
- 保存为今日穿搭、日历计划和发起 AI 试穿。
- 衣橱不足与外部服务失败的完整体验。

## 10. 明确不包含

- 社区、发帖、点赞、评论或关注。
- 淘宝、抖音或其他商品链接。
- 外部商品推荐、联盟佣金和购买归因。
- 多用户、登录、云同步和跨设备数据。
- 自动购买。
- 每次推荐自动生成真人试穿图。
- 基于身材或敏感属性的审美判断。

## 11. 现有项目的必要调整

- 将单个 `index.html` 中的推荐、衣橱、换装、日历和个人设置逻辑拆成独立模块，同时保持现有视觉风格。
- 以 `server.js` 作为唯一后端入口；旧 Python 代理和失效 `Procfile` 不再参与运行，并在迁移确认后归档。
- 修复当前“我的”标签无页面、日历默认固定在 2026 年 3 月、分类映射不完整等与新流程直接相关的问题。
- 保留现有衣橱数据键并提供一次性迁移，避免用户已有本地衣物丢失。

## 12. 交付顺序

1. 安全清理与后端配置。
2. 数据访问层、衣物模型扩展和旧数据迁移。
3. 首次设置、“我的”和天气服务。
4. 衣物图片自动标签及人工编辑。
5. 推荐引擎、Agent 接口和结果校验。
6. 推荐首页、穿搭卡片和连续对话。
7. 日历、反馈及现有 AI 试穿联动。
8. 自动化测试、异常体验和最终验收。
